# 软件架构

## 光猫软件架构

> 本文介绍现代运营商（GPON / XG-PON / XGS-PON）光猫的软件架构。
>
> 不针对某一品牌或型号，而是总结目前主流厂商（中兴、华为、烽火、天邑等）采用的整体设计思路。

---

# 一、整体架构

近年来，大多数运营商光猫已经不再采用传统"一个 Linux + 一堆进程"的设计，而是逐渐形成了分层的软件架构。

典型架构如下：

```text
                Web 管理后台
                      │
                HTTP / HTTPS
                      │
               Web Backend
                      │
                 管理框架(API)
                      │
         DBus / IPC / RPC Framework
                      │
                业务服务(Service)
                      │
             配置数据库(Config DB)
                      │
          Shared Memory Database
                      │
        Flash 持久化配置(User Config)
                      │
               MTD / UBI / UBIFS
```

整个系统可以理解为：

- Web 负责展示
- 管理框架负责接口
- Service 负责业务
- Config DB 负责配置管理
- Flash 负责持久化

---

# 二、Buildroot 宿主系统（Host）

绝大多数运营商光猫都采用 Buildroot 构建宿主系统。

Host 主要负责：

- Linux Kernel
- 驱动
- GPON / XGS-PON
- Ethernet Switch
- Wi-Fi Driver
- Flash
- MTD
- UBI
- VoIP
- IPTV
- TR069
- Mesh
- 管理框架
- 容器管理

Host 一般拥有：

- 所有硬件驱动
- 所有设备节点
- 所有网络接口
- 完整系统权限

Host 通常运行几十到上百个业务进程。

例如：

- httpd
- cspd
- buservice
- mqttd
- voip
- gpon_omci
- dnsmasq
- pppd
- smbd

这些进程构成整个设备的软件主体。

---

# 三、应用容器（Application Container）

近年来越来越多运营商开始采用轻量级 Linux 容器。

通常基于：

- LXC
- namespace
- cgroup

容器内一般运行一个裁剪后的 OpenWrt。

需要注意的是：

这类 OpenWrt **并不是完整路由器系统**。

更多属于：

应用运行环境。

例如：

```plaintext
Host(Buildroot)

↓

LXC

↓

OpenWrt
```

它主要承担：

- Web UI
- App
- UCI
- RPC
- 用户态服务

而：

驱动、网络、PON、WiFi、Switch全部仍由 Host 提供。

因此：

容器实际上属于：

**Application Container（应用容器）**

而不是：

Hardware Container（硬件容器）。

---

# 四、网络模型

容器通常不会拥有独立网络协议栈。

网络资源一般来自 Host。

例如：

```plaintext
Host

br0

eth0

pon0

wlan0

↓

namespace

↓

Container
```

因此容器内iptables、bridge、DHCP等操作最终影响Host，并不是真正拥有独立硬件。

很多设备甚至直接：

Bind Mount：

Host 的：

```plaintext
/var/run/dbus

/tmp

/socket

/etc
```

供容器调用。

---

# 五、容器管理框架

容器通常不会自行启动。

而是由 Host 上的管理框架负责。

常见实现：

## 中兴

ufwmg

Unified Framework Manager

负责：

- 创建容器
- 启动容器
- 停止容器
- Overlay 管理
- Rootfs 管理

通常可以看到：

```plaintext
ufwmg service
```

相关进程。

---

## 华为

SAF

Service Application Framework

负责：

- 生命周期管理
- App 管理
- 容器管理
- 服务调度

部分机型会看到：

```plaintext
saf

safmgr
```

等进程。

---

## 其它厂商

不同厂商名称不同。

例如：

- App Framework
- Service Framework
- Framework Manager

但职责基本一致。

---

# 六、Overlay Rootfs

容器 Rootfs 通常不会直接修改。

一般采用：

```plaintext
Rootfs（只读）

+

Overlay（可写）
```

例如：

```plaintext
rootfs

↓

overlay

↓

最终文件系统
```

修改：

Overlay

即可实现：

永久生效。

升级：

只需替换：

Rootfs。

---

# 七、管理框架（Management Framework）

现代光猫通常拥有统一管理框架。

例如：

- DBus
- RPC
- IPC

统一管理：

Wi-Fi

LAN

WAN

PON

Mesh

DHCP

Firewall

QoS

USB

Storage

Samba

等所有模块。

Web 页面几乎全部通过：

管理框架

访问业务服务。

而不是：

直接修改配置文件。

---

# 八、业务服务（Service）

每个功能通常对应一个业务进程。

例如：

```plaintext
DHCP

↓

Service

↓

Config DB
```

```plaintext
WiFi

↓

Service

↓

Driver
```

```plaintext
TR069

↓

Service

↓

ACS
```

Service 负责：

- 参数检查
- 权限控制
- 配置同步
- 配置持久化

---

# 九、配置数据库（Configuration Database）

现代光猫通常拥有统一配置数据库。

配置流程：

```plaintext
Web

↓

Framework

↓

Service

↓

Shared Memory Database

↓

Save

↓

Flash
```

配置通常不会直接修改：

XML

JSON

INI

等文件。

运行期间：

统一操作：

内存数据库。

只有：

Save

时：

才写入：

Flash。

---

# 十、持久化配置

设备启动时：

```plaintext
Flash

↓

读取配置

↓

解析

↓

加载内存数据库
```

运行过程中：

所有业务：

均访问：

内存数据库。

修改：

```plaintext
Set

↓

Shared Memory

↓

Save

↓

Flash
```

因此：

运行配置

与

持久化配置

通常分离。

---

# 十一、软件分层

整个软件系统可以理解为：

```text
Web UI

↓

Management Framework

↓

Business Service

↓

Configuration Database

↓

Shared Memory

↓

Flash

↓

Kernel

↓

Driver

↓

Hardware
```

这种设计具有：

- 模块解耦
- 配置统一
- 热修改
- 权限控制
- 易于升级
- 易于扩展

也是目前主流运营商光猫普遍采用的软件架构。

---

# 十二、典型特点

现代光猫通常具有以下特点：

- Buildroot 作为宿主系统
- BusyBox 用户空间
- Linux Kernel 提供驱动
- LXC/OpenWrt 作为应用容器
- Host 提供网络和硬件资源
- Overlay 实现可写 Rootfs
- Framework 管理业务服务
- DBus / IPC 提供统一 API
- Shared Memory 管理运行配置
- Flash 保存持久化配置

整体已经逐渐向嵌入式微服务和分层架构演进，而不是传统单体式固件。

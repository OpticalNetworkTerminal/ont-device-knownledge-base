# 常见问题

## 简介

本篇汇总 Linux Embedded 文件系统学习中最常遇到的问题，重点帮助读者把 Rootfs、Firmware、Flash、Overlay、UBI、UBIFS、SquashFS 等概念串起来，避免把不同层级的问题混为一谈。

## 为什么嵌入式设备的 Rootfs 经常是只读的

常见原因有：

- 只读镜像更稳定，运行时不容易被意外破坏
- 压缩文件系统可以显著节省 Flash 空间
- 升级时更适合整体替换
- 配置与运行数据可以放入单独可写层，职责分离更清晰

很多设备采用 `SquashFS + Overlay`，本质上就是“稳定基础系统 + 可写变化层”的组合。

相关章节：

- [Rootfs](./Rootfs.md)
- [SquashFS](./SquashFS.md)
- [Overlay 机制](./Overlay机制.md)

## 为什么修改配置不会直接修改 SquashFS

因为 SquashFS 是只读文件系统。系统运行中的写入请求会被重定向到 Overlay 的上层可写目录或可写分区，所以看到 `/etc` 中的配置变化，并不意味着底层只读 Rootfs 被直接改写。

- [OverlayFS](./OverlayFS.md)
- [SquashFS](./SquashFS.md)

## 为什么恢复出厂后配置会消失

很多设备恢复出厂的动作并不是“重装 Rootfs”，而是：

- 删除 Overlay
- 清空配置分区
- 重建可写层

因此配置消失，系统基础文件却可能保持不变。

这也是为什么“恢复出厂”和“重新刷固件”不是同一件事。

## 为什么 Flash 不能像硬盘一样随便写

因为原始 Flash 具有：

- 擦除单位大于写入单位
- 写前通常需要先擦除
- 擦写次数有限
- 可能出现坏块

因此系统不能把原始 NAND/NOR Flash 简单当成普通块设备使用，需要 MTD、UBI、JFFS2、UBIFS 等专门机制配合。

## 为什么需要 UBI

UBI 解决的不是“文件内容组织”，而是“原始 Flash 上如何可靠地管理擦除块”。它提供：

- 坏块处理
- 磨损均衡
- 逻辑卷抽象

在此基础上，UBIFS 才能更稳定地工作。

## 为什么 UBIFS 不能直接挂载在普通硬盘上

因为 UBIFS 设计目标是运行在 UBI 之上，而 UBI 的下层是原始 MTD Flash。普通硬盘、SSD、eMMC 暴露给 Linux 的通常是块设备接口，不提供 UBI 依赖的底层语义。

所以在块设备场景，更常见的是 Ext4、F2FS 等文件系统。

## 为什么 Buildroot 最终常说“生成 Rootfs”

因为 Buildroot 的核心交付物之一就是根文件系统内容及其镜像形式。它可以把同一套根目录内容输出成多种格式，例如：

- `tar`
- `cpio`
- `ext2/ext4`
- `squashfs`
- `ubifs`

之后项目再根据设备需要，把这些产物封装成最终 Firmware。

## 为什么 Factory Firmware 和 Upgrade Firmware 不一样

因为两者面对的刷写入口不同：

- Factory Firmware 更面向首次刷写、恢复或系统迁移
- Upgrade Firmware 更面向已有系统上的在线升级

因此它们的封装格式、校验方式、包含内容与保留配置策略经常不同。

## 为什么很多升级包里没有 Bootloader

因为在线升级场景通常希望降低高风险操作。Bootloader 写坏后设备可能无法正常启动，也不一定还能进入常规恢复流程，所以很多升级包只更新 Kernel 与 Rootfs，不更新 Bootloader。

## 为什么解包 Firmware 后经常看到 SquashFS

因为很多嵌入式系统的 Rootfs 使用 SquashFS。使用 `binwalk`、`unsquashfs` 等工具时，往往可以在 Firmware 某个偏移处识别并解出该只读根文件系统。

但要注意：

- 看见 SquashFS 只说明识别到了 Rootfs 段
- 不代表整个 Firmware 外层封装就只有 SquashFS

## 为什么 OpenWrt 升级通常不会丢配置

因为 OpenWrt 常把只读系统层和可写配置层分开：

- 升级主要替换 Rootfs
- 配置主要保存在 Overlay

因此只要升级逻辑没有清除 Overlay，配置就能保留。

## 为什么 OpenWrt 恢复出厂通常只是删除 Overlay

因为 Overlay 承担了运行时配置与改动保存职责。删除它后，系统又回到只读 Rootfs 提供的初始状态，这对恢复出厂来说已经足够。

## 如何快速判断设备更接近哪种文件系统路线

可以先问三个问题：

1. 底层是原始 Flash 还是块设备
2. Rootfs 是只读镜像还是可写文件系统
3. 配置位于 Overlay、独立分区还是独立 volume

如果是原始 NAND Flash，常见路线更接近：

`MTD -> UBI -> UBIFS`

如果是只读压缩根文件系统，常见路线更接近：

`SquashFS -> Overlay`

如果是 eMMC、SSD、SD 卡等块设备，常见路线更接近：

`Block Device -> Ext4 / F2FS`

## 实践操作

### 1. 看系统当前使用了哪些文件系统

```bash
cat /proc/filesystems
```

作用：

- 查看内核当前支持哪些文件系统类型

怎么看：

- 如果看到 `squashfs`、`ubifs`、`overlay`，说明内核具备相应支持

### 2. 看系统当前实际怎么挂载

```bash
cat /proc/mounts
findmnt
```

作用：

- 查看 `/`、`/overlay`、`/proc`、`/sys`、`/dev` 的实际来源

怎么看：

- 如果 `/` 是 overlay，而 lowerdir 指向只读系统层，说明配置与系统基础层已经分离

### 3. 看 MTD 和 UBI 信息

```bash
cat /proc/mtd
ubinfo
```

作用：

- 确认是否使用原始 Flash 与 UBI

怎么看：

- `/proc/mtd` 有内容通常表示设备使用了 MTD 管理原始 Flash
- `ubinfo` 能看到 volume 时，说明设备上层很可能使用 UBI / UBIFS

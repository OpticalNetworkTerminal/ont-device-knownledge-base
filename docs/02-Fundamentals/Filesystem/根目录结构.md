# 根目录结构

## 简介

本文说明 Linux Embedded 系统根目录中常见目录的职责，以及为什么嵌入式 `Rootfs` 的目录组织通常比桌面发行版更克制。

## 背景

看到一个 Rootfs 时，很多人第一反应是找应用程序；但真正决定系统能否启动和可否恢复的，是 `/bin`、`/sbin`、`/etc`、`/lib`、`/proc`、`/sys`、`/dev`、`/tmp` 这些目录如何分工。

## 基本概念

- `/bin`、`/sbin`：基础命令与系统管理命令
- `/etc`：配置入口
- `/lib`：运行时共享库和内核模块相关内容
- `/proc`、`/sys`、`/dev`：运行时 API 面
- `/tmp`、`/var`：临时或可变状态

## 工作原理

目录结构既受 FHS 影响，也受嵌入式裁剪影响。很多设备会把可变内容尽量移到独立可写层，而把系统本体维持在只读镜像内。

## 设计目的

- 帮助快速阅读陌生 Rootfs
- 理解哪些目录适合持久化、哪些目录本来就是运行时生成
- 为后续 Overlay 和固件分析建立目录层语义

## 优缺点

优点：

- 看目录树就能快速判断设备架构风格
- 便于识别只读系统与可写状态的分界

缺点：

- 不同发行版和设备的细节差异较大
- 目录存在不代表数据一定持久化

## 典型应用

- 解包固件后的 `rootfs/` 目录检查
- 判断 `/etc` 改动是否会落入 Overlay

## 在 Buildroot 中的位置

Buildroot 负责生成目标文件树，目录层次通常会比桌面发行版更精简，但基本角色仍保留。

## 在 OpenWrt 中的位置

OpenWrt 把配置主要放在 `/etc/config`，并通过 Overlay 让这些文件变成“逻辑上可写”。

## 在光猫中的体现

光猫和 IoT 设备往往保留最少目录集，很多日志、PID、socket 放在 `/tmp` 或 `/var/run` 之类的易失区域。

## 实际案例

为什么修改 `/etc` 某些文件后 reboot 会丢失，而另一些配置又能保留？关键不在目录名，而在这些路径最终是来自只读层、可写层，还是启动脚本动态生成。

## 实践操作

```bash
ls /
du -sh /etc /bin /sbin /lib 2>/dev/null
mount | grep -E " / | /tmp | /var | /proc | /sys | /dev "
```

怎么看：

- `ls /`：看目录骨架是否精简
- `du`：看系统体积主要集中在哪些目录
- `mount`：确认这些目录是普通目录、独立文件系统，还是 Overlay 目标

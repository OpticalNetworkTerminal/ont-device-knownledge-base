# 常见问题

## 简介

本文汇总 Linux 嵌入式运行环境里最常见的兼容性问题，并给出排查主线。

## 背景

很多“程序不能运行”的问题，表面报错相似，底层原因却完全不同。必须建立一套由外到内的判断顺序。

## 基本概念

最常见的问题类型：

- 架构不匹配
- 位宽不匹配
- 端序不匹配
- ABI 不匹配
- 动态链接器缺失
- libc 不匹配
- 共享库缺失

## 工作原理

排查顺序建议始终遵循：

1. 先看 `file`
2. 再看 `readelf -h`
3. 再看 `readelf -l`
4. 再看 `readelf -d`
5. 最后再看 `ldd`

## 设计目的

把问题定位从“凭经验猜”变成“按运行环境层次收缩”。

## 优缺点

优点：

- 能快速缩小范围
- 适合 Buildroot / OpenWrt / 光猫 Rootfs 通用场景

缺点：

- 需要对 ELF、ABI、libc 有基本理解

## 典型应用

- 判断 `No such file or directory`
- 判断 `Exec format error`
- 判断“库明明在，还是跑不起来”

## 在 Buildroot 中的位置

Buildroot FAQ 明确解释过：目标系统默认不是开发环境，也不一定包含编译器和开发文件。很多误解都来自把运行环境和开发环境混淆。

## 在 OpenWrt 中的位置

OpenWrt 由于 Rootfs 可写、包管理更活跃，容易让人误以为它更接近通用发行版，但底层 ABI 和 libc 兼容性问题并没有消失。

## 在光猫中的体现

光猫现场最常见的误区是：

- 看到两个设备都是 Linux，就以为程序可互拷
- 看到两个程序都叫 ARM ELF，就以为一定兼容

## 实际案例

### 为什么复制一个二进制过去会报 `No such file or directory`

常见根因：

- `INTERP` 指向的动态链接器路径不存在
- 不是程序文件本身缺失

### 为什么 `file` 显示 `ELF 64-bit LSB shared object`

可能是共享库，也可能是 PIE 可执行文件，不能只靠这一行下结论。

### 为什么 glibc、musl、uClibc 不能混用

因为它们不是“同一个 libc 的不同包”，而是不同运行时实现，动态链接器、符号、行为和 ABI 契约都不同。

## 实践操作

```bash
file busybox
readelf -h busybox
readelf -l busybox
readelf -d busybox
ldd busybox
```

怎么看：

- `file`：先排除架构和位宽问题
- `readelf -l`：先确认解释器
- `readelf -d`：确认依赖库
- `ldd`：确认当前环境实际解析

# 静态链接

## 简介

本文说明静态链接的原理，以及它与动态链接在嵌入式 Linux 中的取舍。

## 背景

有些开发者会问：既然动态链接这么容易出兼容问题，为什么不全部静态链接？答案是：静态链接能减少运行时依赖，但也会带来体积、升级、许可证和复用问题。

## 基本概念

静态链接指在链接阶段把需要的库代码直接合并进最终二进制，运行时不再依赖外部共享库。

## 工作原理

链接器会从静态库中挑选需要的目标代码，合并到最终 ELF。运行时内核直接装载该程序，不需要额外装载大量共享库。

## 设计目的

- 减少运行时外部依赖
- 方便单文件部署
- 在极简系统中提供更稳定的可运行性

## 优缺点

优点：

- 部署简单
- 少依赖目标 Rootfs 的库文件

缺点：

- 二进制体积更大
- 多程序重复包含相同库代码
- 安全更新时不能只更新共享库

## 典型应用

- 恢复工具
- 单用途诊断工具
- 某些极简嵌入式程序

## 在 Buildroot 中的位置

Buildroot 可以支持静态链接构建，但大多数完整 Rootfs 仍会混合使用动态链接方案，特别是需要共享 libc 的场景。

## 在 OpenWrt 中的位置

OpenWrt 更常强调包与共享库依赖关系，因此动态链接更常见，但某些小工具也可能静态构建。

## 在光猫中的体现

光猫环境中，静态链接程序有时被用于：

- 恢复模式工具
- 维护诊断程序
- 在受限环境下减少依赖

但大规模业务程序通常仍以动态链接为主。

## 实际案例

静态 BusyBox 常被用作救援环境，因为只要 CPU 架构兼容，它比动态链接版本更不依赖目标 Rootfs 的共享库。

## 实践操作

```bash
file busybox
readelf -l busybox
readelf -d busybox
ldd busybox
```

怎么看：

- 若 `readelf -d` 没有动态段，往往更接近静态链接
- `ldd` 对静态程序通常不会列出常规动态库依赖

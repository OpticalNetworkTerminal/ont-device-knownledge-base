# 插件管理

## 目标

整理 ZTE 光猫中“运营商插件 / 插件管理服务 / 插件框架”的常见查看、控制与禁用方法。

## Evidence

C

## 当前结论

在部分较新的 ZTE ONT 固件中，存在一套独立于 `sendcmd` 的插件管理机制。公开资料显示：

- `appmgr` 是插件管理核心启动服务
- system bus 上可见 `com.ctc.appframework1`
- 可通过 `gdbus` 调用 `AppAgent.List`、`GetStatus`、`Stop`、`Run`
- 从 `/etc/init.d/appmgr` 根源禁用，比只停单个插件更彻底

## 适用范围

当前公开样本主要来自：

- F7615TV3
- F7615V2
- F7015TV3

这不等于所有 ZTE ONT 都有相同插件框架，也不等于对象名、脚本路径和行为完全一致。

## 查看插件

### 列出插件

```sh
gdbus call -y -d com.ctc.appframework1 -o /com/ctc/appframework1 -m com.ctc.appframework1.AppAgent.List
```

### 查询单个插件状态

```sh
gdbus call -y -d com.ctc.appframework1 -o /com/ctc/appframework1 -m com.ctc.appframework1.AppAgent.GetStatus <插件名>
```

### 停止单个插件

```sh
gdbus call -y -d com.ctc.appframework1 -o /com/ctc/appframework1 -m com.ctc.appframework1.AppAgent.Stop <插件名>
```

### 启动单个插件

```sh
gdbus call -y -d com.ctc.appframework1 -o /com/ctc/appframework1 -m com.ctc.appframework1.AppAgent.Run <插件名>
```

## 根源禁用 appmgr

这是目前公开资料中更彻底的方案。

### 步骤

1. 先通过 Telnet 以 `root` 登录。
2. 进入 `saf console`。
3. 打开 `/etc/init.d/appmgr`。
4. 注释 `start_service()` 内的启动代码。
5. 保存退出后重启。
6. 重启后检查 `appmgr`、插件进程和 `AppAgent.List` 输出。

### 参考操作

```sh
telnet 192.168.1.1
saf console
cd /etc/init.d
vi appmgr
```

`start_service()` 样本：

```sh
start_service(){
#       procd_open_instance
#       procd_set_param command "$PROG"
#       procd_set_param respawn 3600 5 0
#       procd_close_instance
}
```

保存后可验证：

```sh
cat /etc/init.d/appmgr | grep start_service -A 5
ps | grep appmgr
ps | grep -E "v3|plugin|gamespeeder|opmaintain"
gdbus call -y -d com.ctc.appframework1 -o /com/ctc/appframework1 -m com.ctc.appframework1.AppAgent.List
```

## 恢复方式

若只是改坏了 `appmgr` 脚本，社区资料给出的恢复方式是：

```sh
cp /rom/etc/init.d/appmgr /etc/init.d/appmgr
```

然后重新编辑或重启。

## 风险

风险等级：高

主要风险：

- 光猫拨号场景下，关闭全部插件后可能导致 IPv6 不稳定
- 远程运维、日志上报、插件自动更新会一起失效
- 不同型号固件的插件框架可能不同
- 错误编辑 `/etc/init.d/appmgr` 会影响开机启动流程

## 已知副作用

目前社区已明确反馈的一条副作用是：

- 如果由光猫负责拨号，关闭全部插件后可能出现 IPv6 前缀能获取，但下游设备难以正常拿到 IPv6 地址的情况

因此：

- 纯桥接场景更适合使用本方法
- 光猫继续承担拨号、IPv6 RA、家庭网关功能时需要更谨慎

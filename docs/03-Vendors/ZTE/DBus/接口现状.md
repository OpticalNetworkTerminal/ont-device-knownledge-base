# 接口现状

## 当前状态

早期文档只能确认 ZTE 设备存在 `sendcmd`、`sidbg`、XML 配置和私有管理接口，不能确认是否存在完整 DBus 模型。

本次 `DBus Explorer` 采集后，至少对当前样本设备可以确认：

- 存在 system bus 上的 `com.cuc.igd1`、`com.cuc.ufw1`、`com.cuc.uappd1`、`com.cuc.appframework1`。
- `com.cuc.igd1` 是家庭网关核心业务 Service。
- `com.ctc.appframework1` / `com.cuc.appframework1` 一类插件框架接口在线索中稳定出现。
- 业务对象可统一抽象为 Service/Object/Interface/Method/Property/Signal。
- 设备使用厂商自定义 `com.cuc.igd1.Properties` 和 `com.cuc.igd1.ObjectManager`。

## 插件管理接口线索

社区资料已明确给出一组插件管理接口样本：

- Service：`com.ctc.appframework1`
- Object：`/com/ctc/appframework1`
- Interface：`com.ctc.appframework1.AppAgent`
- Method：
  - `List`
  - `GetStatus`
  - `Stop`
  - `Run`

对应命令样本：

```sh
gdbus call -y -d com.ctc.appframework1 -o /com/ctc/appframework1 -m com.ctc.appframework1.AppAgent.List
gdbus call -y -d com.ctc.appframework1 -o /com/ctc/appframework1 -m com.ctc.appframework1.AppAgent.GetStatus <插件名>
gdbus call -y -d com.ctc.appframework1 -o /com/ctc/appframework1 -m com.ctc.appframework1.AppAgent.Stop <插件名>
gdbus call -y -d com.ctc.appframework1 -o /com/ctc/appframework1 -m com.ctc.appframework1.AppAgent.Run <插件名>
```

## 当前理解

- 这说明“插件管理”至少在部分机型中已经不是纯 Web 页面逻辑，而是有单独总线接口。
- `appmgr` 负责启动层，`AppAgent` 更像运行时管理层。
- `ctc` 与 `cuc` 前缀是否对应不同运营商或不同固件实现，仍需继续按设备区分。

## 仍不能扩大化的结论

以下结论仍需按设备型号和固件版本分别验证：

- 所有 ZTE 光猫都暴露同一套 DBus。
- `sendcmd` 是 DBus 的直接封装。
- 不同运营商固件的对象路径和字段完全一致。
- Web 后台一定直接调用 DBus，而不是通过中间守护进程间接调用。
